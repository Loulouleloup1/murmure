# yt-dlp feasibility spike — subprocess spawn from a Swift app, no Homebrew

Machine: macOS 26.6.2 (Darwin 25.6), arm64. Homebrew ffmpeg/node present but bypassed via `env -i HOME="$HOME" PATH=/usr/bin:/bin:/usr/sbin:/sbin` for every step marked "restricted PATH".

Binary: `yt-dlp_macos` release `2026.08.19`, downloaded via curl.
Size: 37,146,048 bytes. SHA-256: `0f192b7ec147ab6288885d6351d9ab67367640029b4377576ef46dd79cf7b202`.

## Findings

- **(a) Gatekeeper handling needed:** None, in practice. `curl -L` does not set `com.apple.quarantine` (only `com.apple.provenance`), so the ad-hoc-signed binary ran on first try with no `xattr -d`, no `codesign -s -`, and no dialog. `spctl` still flags it as `rejected` in isolation, but that check is never triggered without the quarantine bit — so it's harmless. **Caveat:** an app that downloads the binary via `URLSession`/`NSURLDownload` or lets the user drag it in via Finder/Safari *will* pick up the quarantine flag, and then Gatekeeper *will* need `xattr -d com.apple.quarantine` (self-fixable in-process, no user dialog needed) since the binary is only ad-hoc signed, not notarised.
- **(b) JS runtime needed for YouTube today:** Not strictly required for this test video — `-F` and the audio-only download both succeeded with just a WARNING ("No supported JavaScript runtime could be found... some formats may be missing"). Only `deno` is enabled by default and it isn't present without Homebrew; extraction still worked because the audio-only DASH/HTTP formats didn't need the JS-gated signature. Cannot generalise to all videos (some require PO-token/JS-signature solving that may hide formats or fail entirely) — this was one 19-second public video with no bot-check.
- **(c) Can we avoid ffmpeg:** Yes for YouTube, if you pick `bestaudio[ext=m4a]` — Core Audio/`afconvert`/AVFoundation opens the raw DASH m4a directly despite yt-dlp's own "install ffmpeg to fix this" warning. The **Opus/webm** stream is a hard no — `afconvert`/`afinfo` fail outright on it, so any code path that could pick a webm/Opus audio format needs ffmpeg (or must force the format selector to `bestaudio[ext=m4a]/bestaudio[acodec^=mp4a]`, never a bare `bestaudio`, which could resolve to Opus). Also true for X: the audio-only HLS AAC track downloads and decodes fine natively.
- **(d) X works without login:** Yes — the SpaceX test post came back with a full format list and downloaded audio using only a guest token, no cookies, no login wall.
- **(e) Progress parseability:** Workable but not clean out of the box. `--progress-template` gives literal control over the printed line, but percent has variable leading padding and ETA renders as the *strings* `Unknown`/`NA` rather than a number/sentinel — a Swift subprocess reader should trim whitespace and treat `Unknown`/`NA` as "no ETA yet" rather than parsing them as numbers.
- **(f) Surprises:**
  1. `curl` downloads never carry `com.apple.quarantine` — this eliminates the Gatekeeper concern for a Swift app that fetches the binary itself over HTTP rather than through a quarantine-aware API.
  2. yt-dlp's official binary is **already ad-hoc signed** by the maintainers (not just "unsigned"), which is why the naive `codesign -dv` output looked slightly better than expected but still shows `TeamIdentifier=not set` (not Developer ID/notarised).
  3. yt-dlp explicitly warns when it writes a container Core Audio technically can't fully validate (DASH m4a, "malformed AAC timestamps" on the X HLS mux) yet `afconvert`/`afinfo` decoded both anyway — the warnings are about strict-player compatibility, not about whether AVFoundation can read the file.
  4. Two of three "native X video" candidates found via web search were red herrings: a NASA tweet whose only media was a `t.co` link to an external nasa.gov article, and an ESA tweet whose "video" was actually an embedded YouTube player — yt-dlp transparently followed both through the `[generic]`/`[youtube]` extractors, which is worth knowing since it means `-F` succeeding on an X URL doesn't guarantee the video is X-hosted.
  5. Every yt-dlp invocation (even `--version`) costs ~9–13 s wall time on this machine, which is the PyInstaller onefile-binary self-extraction overhead, not a network or Gatekeeper cost — worth caching a "warm" extracted copy or reusing a long-lived process in the real app if per-call latency matters.
