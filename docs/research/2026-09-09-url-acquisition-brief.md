# URL-to-audio acquisition for a local Swift dictation app (YouTube/X -> WhisperKit)

## Actionable bullets
1. Ship yt-dlp as a **downloaded, self-updating binary** in `Application Support`, not a bundled/pip dependency — 2026 releases still ship a macOS standalone binary, and YouTube's anti-bot defences change often enough that pinning a bundled version will rot within weeks.
2. Bundle **ffmpeg** too: `-x`/`-f bestaudio` audio extraction hard-requires it for stream merging/transcoding ([huntapi.com](https://www.huntapi.com/blog/using-ffmpeg-with-yt-dlp), [snapcraft.io forum](https://forum.snapcraft.io/t/yt-dlp-cant-extract-audio-ffmpeg-is-needed/31572)) — do not try to avoid it via AVFoundation-only decoding.
3. YouTube in 2026 requires a **JS-challenge solver** (Deno/Node/Bun/QuickJS) for the n-parameter/signature and increasingly for PO tokens ([yt-dlp #14404](https://github.com/yt-dlp/yt-dlp/issues/14404), [DeepWiki](https://deepwiki.com/yt-dlp/yt-dlp/3.4.2-javascript-challenge-solving)) — plan to ship or auto-fetch a Deno runtime, or accept intermittent failures.
4. X/Twitter extraction still works for public videos without login as of early 2026 patches, but NSFW/protected/age-gated content needs browser cookies ([yt-dlp #11770](https://github.com/yt-dlp/yt-dlp/issues/11770)) — design a "paste cookies file" escape hatch, don't block on it.
5. A downloaded `yt-dlp`/`ffmpeg` binary will hit Gatekeeper on first launch via `Process` — must clear `com.apple.quarantine` and apply an ad-hoc `codesign -s -` after download, before spawning ([Storbeck](https://www.storbeck.dev/posts/macos-code-signing-patched-binaries), [HackTricks](https://hacktricks.wiki/en/macos-hardening/macos-security-and-privilege-escalation/macos-security-protections/macos-gatekeeper.html)).

## Brief

**1. yt-dlp state.** Release cadence is frequent (dated builds, e.g. 2026.06.09, 2026.08.19 via MacPorts — [videoproc.com](https://www.videoproc.com/download-record-video/how-to-update-yt-dlp.htm)). YouTube pushes breaking changes regularly: an open tracking issue ([#14404](https://github.com/yt-dlp/yt-dlp/issues/14404)) covers "upcoming new requirements," and 2026 issues show `PO Token providers: none` failures and `n challenge` solver errors ([#15684](https://github.com/yt-dlp/yt-dlp/issues/15684), [#16821](https://github.com/yt-dlp/yt-dlp/issues/16821)). yt-dlp's own JS-challenge subsystem now runs Deno (default, sandboxed) or Node/Bun/QuickJS with explicit user opt-in ([DeepWiki](https://deepwiki.com/yt-dlp/yt-dlp/3.4.2-javascript-challenge-solving)); a third-party Deno-solver plugin is now marked **obsolete** in favour of the native support ([bashonly/yt-dlp-YTNSigDeno](https://github.com/bashonly/yt-dlp-YTNSigDeno)). One search noted the macOS standalone binary was "dropped earlier in 2026" per a MacRumors forum thread, contradicting the official wiki/release page still listing a macOS binary — see Contradictions. Shipping model: `brew`/`pipx` are non-starters for a non-sandboxed but self-contained signed app (can't assume a user Homebrew/Python); download the official release binary at first use into `Application Support`, then self-update via `-U` (channel-scoped) or `--update-to CHANNEL` ([yt-dlp wiki](https://github.com/yt-dlp/yt-dlp/wiki/Installation)). ffmpeg is required for `-x`/audio extraction regardless of container ([huntapi.com](https://www.huntapi.com/blog/using-ffmpeg-with-yt-dlp)) — bundle or auto-download it alongside. Typical failure modes to design for: bot-check walls ("Sign in to confirm you're not a bot," [#15865](https://github.com/yt-dlp/yt-dlp/issues/15865)), missing/failed JS-challenge solver, stale binary against a new YouTube player version, and missing ffmpeg.

**2. X/Twitter.** yt-dlp maintains a dedicated `twitter.py` extractor ([source](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/twitter.py)) and public, unrestricted videos extract without login in recent 2026 point releases. Known gaps: NSFW-flagged tweets require auth ([#11770](https://github.com/yt-dlp/yt-dlp/issues/11770)), historic reports of "account now required" for some paths ([#7473](https://github.com/yt-dlp/yt-dlp/issues/7473), older), Spaces (audio rooms) and protected/private accounts need `--cookies-from-browser`. No credible alternative extractor was found specifically for X in 2026 searches; yt-dlp remains the de facto standard.

**3. Alternatives.** No actively maintained Swift-native YouTube/X extraction library surfaced (XCDYouTubeKit is long dead post player-signature changes; no credible 2026 successor found). Cobalt: the **public** cobalt.tools instance is blocked by YouTube's anti-downloader measures as of 2026; only a **self-hosted** Cobalt instance (e.g. via Railway) still works ([Railway deploy page](https://railway.com/deploy/cobalt-youtube-downloader), [any-video-converter.com roundup](https://www.any-video-converter.com/hot-topic/cobalt-tools-alternative.html)) — but self-hosting defeats the "fully local, single Mac app" goal and just relocates the same extraction problem to a server you maintain. Invidious/Piped instances are third-party-hosted and notoriously unstable/rate-limited; not mentioned as viable in current results. **Conclusion: yt-dlp (shelled out to) remains the only maintained, broad-coverage option** for a solo macOS app in 2026.

**4. Legal/ToS (not legal advice).** YouTube's ToS prohibit downloading absent an explicit "download" affordance; enforcement in practice targets redistribution/scraping-at-scale, not a single user's personal, local, non-shared use. Commercial Mac apps normalise this: MacWhisper offers direct "paste a YouTube URL" transcription and documents a yt-dlp-based workflow ([Simon Willison TIL](https://til.simonwillison.net/macos/quick-whisper-youtube), [MacWhisper site](https://macwhisper.org/)); Downie (Software Ambience) is built specifically around yt-dlp-family extraction and is sold on the Mac App Store and directly. In an EU/France personal-use context this sits in the same "commonly tolerated, ToS-violating but not enforced against individuals" zone as most desktop YouTube downloaders — flag to the user as a known grey area, not a green light.

**5. Existing apps.** MacWhisper: accepts a YouTube URL directly in its UI; workflow evidence points to an internal yt-dlp-style fetch (not confirmed as literally bundled yt-dlp) rather than a documented public bundling statement ([daveswift.com review](https://daveswift.com/macwhisper/), [snailtext.app](https://snailtext.app/blog/does-macwhisper-transcribe-audio/)). No 2026 evidence found in this pass for Superwhisper's URL-input support specifically, nor for VoiceInk/Whisper Transcription/Aiko's YouTube handling — flagged as a gap below.

**6/7. Formats & subprocess mechanics.** yt-dlp's `bestaudio` for YouTube typically resolves to `m4a` (AAC ~128 kbps) or `webm` (Opus) depending on itag availability; extracting via `-x` re-encodes through ffmpeg regardless, sidestepping the container question — so **shipping ffmpeg removes the need to test AVFoundation's native WebM/Opus decode path**. Native AVFoundation support for Opus-in-WebM specifically was not confirmed either way by search results (Opus-in-CAF/mp4 support was added years ago per an old Hacker News thread; WebM container demuxing is the unresolved part) — treat as a gap, and avoid it operationally by always routing through ffmpeg to m4a/wav before feeding WhisperKit. For subprocess integration: yt-dlp supports `--newline` (line-buffered progress) and `--progress-template` for structured, parseable progress lines — pipe stdout through a `Process`/`Pipe` reader. Store the binary under `~/Library/Application Support/<AppID>/bin/`. After download, **strip quarantine** (`xattr -d com.apple.quarantine <path>`) and **apply an ad-hoc signature** (`codesign -s - --force <path>`) before the first `Process.run()`, or Gatekeeper/`spctl` will block execution with an unverified-developer error even when launched programmatically ([Storbeck](https://www.storbeck.dev/posts/macos-code-signing-patched-binaries), [HackTricks](https://hacktricks.wiki/en/macos-hardening/macos-security-and-privilege-escalation/macos-security-protections/macos-gatekeeper.html)). A non-sandboxed, non-App-Store app can do this itself at runtime without extra entitlements.

## Recommendation

**Ship yt-dlp (+ ffmpeg) as a first-use download with self-update**, not a Swift-native alternative and not Cobalt. Rationale: no maintained Swift library exists; Cobalt only works self-hosted (adds server ops, doesn't remove the extraction fragility); yt-dlp is the only option with an active team tracking YouTube's near-weekly countermeasures. Concretely: download official binaries to Application Support on first use -> `xattr -d com.apple.quarantine` + ad-hoc `codesign` -> run with `--newline --progress-template` for UI progress -> `-x --audio-format wav` (or m4a) via ffmpeg, feeding WhisperKit -> periodic `yt-dlp -U` (or a manual "check for extractor update" button, since YouTube breakage is bursty) -> a cookie-file import path for X content requiring auth. Budget for user-visible failure states (bot-check, missing solver, stale extractor) since these are yt-dlp's most common 2026 complaints.

## Contradictions

1. **yt-dlp macOS standalone binary availability.** A MacRumors forum thread claims the macOS standalone binary "was dropped earlier in 2026." The official yt-dlp GitHub Releases page and Installation wiki (queried same session) still describe a macOS binary download path with no such deprecation notice. **Verdict: ouverte.** A forum post is not authoritative against the project's own release page, but the release page wasn't opened directly (only indexed via search) in this pass. Ask: check `https://github.com/yt-dlp/yt-dlp/releases/latest` directly for a macOS asset before committing to the "download official binary" step of the recommendation.
2. **X/Twitter login requirement.** Search snippets show both "account is now required to download" (issue #7473, contextually older/2023-vintage per issue numbering) and current 2026 patch notes implying public video extraction still works without login. **Verdict: résolue (partially), via the extractor source itself** — `yt_dlp/extractor/twitter.py` (fetched by title, not fully read) is the canonical current behaviour; #7473 reads as a historical/since-fixed report given its low issue number relative to 2026-era issues (#15xxx–#17xxx). Residual uncertainty on Spaces/protected accounts remains genuinely open — ask: none, treat as known limitation, not a contradiction to chase further.

## Gaps
- AVFoundation's native ability (or inability) to decode Opus audio inside a WebM container was not confirmed by search — moot for this design (ffmpeg re-encode is the recommended path) but worth a 10-minute manual test (`AVAsset` load on a raw `.webm` from yt-dlp without `-x`) if the app ever wants to skip the ffmpeg dependency.
- Superwhisper's URL/file-input capability and VoiceInk/Whisper Transcription/Aiko's YouTube handling were not found in this pass — needs a direct search per app name + "YouTube" + 2026, or a check of their own docs/changelogs.
- Whether MacWhisper's YouTube-URL feature is literally bundled yt-dlp or a proprietary fetcher is unconfirmed — would need MacWhisper's release notes or binary inspection (out of scope: no downloads).
- No official Apple/EU statement was sought on personal-use downloading legality — intentionally out of scope per the "not legal advice" framing; if actually needed, route to a lawyer, not more web search.
